# A2UI 行程修改预览接入规格

- 状态：待实现（口径已裁决，见 §9）
- 范围：第一期，仅咕噜对话中的行程修改预览
- 使用方：Funny+ ReactLynx 客户端；iOS、Android、Web
- 日期：2026-11-17

## 1. 背景和目标

当前助手通过 `onRevise` 接收服务端产生的 `RevisePreview`，由 AssistantPage 固定渲染卡片，用户确认后调用现有行程更新逻辑。本期引入 Lynx 官方 A2UI 渲染器，将这张卡片作为受控组件渲染，验证消息处理、动作回传、跨端表现与失败降级。

成功条件：用户提出修改后，在三端均可看到与现有卡片等价的预览，并可确认或取消；失败时现有预览仍可用。此阶段由客户端确定性生成 A2UI 消息，不要求模型生成或选择 UI，不改变现有对话服务端协议。

## 2. 范围

### 包含

1. 引入兼容当前 ReactLynx 的 `@lynx-js/genui/a2ui`（含 peer `@lynx-js/lynx-ui`），明确并锁定依赖及协议版本。
2. 注册行程修改预览组件及确认、取消动作；从现有 `RevisePreview` 生成协议消息。
3. 保留每轮原始预览和现有预览 UI；A2UI 失败时展示旧 UI。
4. 防止重复确认，以及旧预览覆盖已变化的行程。
5. 验证 Web、iOS、Android，以及流式和非流式对话路径。

### 不包含

模型生成 A2UI 消息或动态选择组件、修改服务端接口、改造其他对话卡、重设计工作台、账号同步、移除旧预览或改变引擎计算规则。预览跨页面持久化、无障碍名称、组件渲染测试基建同样不属于本任务。地图和 SVG 图标迁移不属于本任务。

## 4. 功能需求

### FR-1 预览生成和展示

收到有效 `RevisePreview` 后，创建 previewId 和渲染上下文，将引擎返回的数据转换为安装版本支持的 A2UI 消息。卡片须包含现有预览所显示的原因、受影响项目、时间变化、人均费用变化、需重新确认事项及引擎兜底提示。保留现有格式、单位和正负号；空列表按原卡片口径处理。不得从模型文本推导或补造数字、地点和事实。同轮多次预览的取舍见 FR-5。

A2UI 消息仅为展示产物；原始 `RevisePreview` 是本次操作的业务依据。不同轮次的卡片、数据和状态互不串扰。

### FR-2 确认与取消

卡片仅开放确认和取消两个动作。动作只传 previewId，客户端依据它查找本轮保存的原始预览，再走现有 `onApplyRevise` 或取消处理；禁止以动作载荷中的计划、费用或其他字段覆盖原始预览。未知动作、未知 previewId 和非 pending 预览均忽略并记录可诊断信息。

确认操作在同一预览的生命周期内最多触发一次应用：处理开始时立即锁定，成功后卡片显示「已写进行程」并保留在对话页，不再自动跳转行程页。取消后卡片移除，不可再确认，且不修改行程。应用为同步提交，不设中间态与卡片级失败重试。

### FR-3 过期预览

生成预览时记录基准：`tripId + planIndex + 当前 plan 的对象引用`，三者任一变化即判过期。不用 `versions.length` 作版本号：`pickPlan` 与 `changeCity` 不写 versions，会漏判。现有修改入口共 6 个（`revisePlan` / `pickPlan` / `changeCity` / `switchTrip` / `deleteTrip` / `createTrip`），均产生新的 store 对象，故引用比较可覆盖全部入口。确认前再次核对，不一致则拒绝应用、标记过期并提示重新生成，不得静默覆盖较新行程。作用域限于同一对话页面会话：预览不持久化，跨页面回来时卡片已不存在（见 §3）。

### FR-4 降级

依赖未启用、消息转换失败、协议或 Catalog 拒绝、渲染未就绪或运行时失败时，保留原始预览并显示现有卡片。`A2UI` 的 `renderError` / `renderUnsupported` 只覆盖协议与组件不支持，不捕获子树抛错；运行时抛错须自行用 `@lynx-js/react` 的 `useErrorBoundary` 包一层。旧卡片和新卡片必须共用同一确认、取消、过期及防重入口，避免降级绕过约束。降级不得重复发起模型请求、重复应用变更或丢失已有对话内容。

### FR-5 对话通道和生命周期

流式、非流式均使用现有工具结果处理路径，不改变服务端响应。每份预览有唯一 previewId，作为动作与状态的唯一键；不使用轮次下标，因为从本机恢复的历史只有 role / text，下标与原始轮次不对应。一轮只保留最后一份预览，同轮后一次 `proposeRevise` 覆盖前一次，被覆盖的 previewId 立即失效。每个对话轮次独立维护 A2UI store 和 surface；重渲染不重置已处理状态，轮次销毁时释放对应资源。切换 store 时按官方要求以 `key` 重建处理器（`A2UIProps` 注释明确要求），避免数据泄漏到其他轮次。重试或部分流失败时，同一预览不应被重复显示或应用。

### FR-6 UI

沿用旧卡片视觉、文本与按钮语义；长原因和地点列表可完整阅读，费用负值、零值、正值与未知状态按既有模型正确呈现。不可仅以颜色区分确认、取消或兜底状态。本期不新增无障碍名称要求（全仓无先例，另立规格时再评估）。

## 5. 数据及动作边界

| 数据 | 所有者 | 规则 |
| --- | --- | --- |
| 行程、影响、费用、待确认事项 | 现有引擎和 `RevisePreview` | 客户端只作格式转换，不由模型或 A2UI 补算 |
| previewId、基准、状态 | 客户端本轮会话 | 唯一、稳定；基准为 `tripId + planIndex + plan 引用`；确认前校验；不作为永久行程数据 |
| A2UI 消息 | 客户端适配器 | 根据锁定版本的 schema 生成，仅用于展示 |
| Action | A2UI 组件 | 限定动作名和 previewId；经白名单检查后交给业务层 |
| 行程持久化 | 现有应用逻辑 | 沿用现有行为；A2UI 不直接写存储 |

预览状态为 `pending → applied`、`pending → stale`；取消不保留状态，直接丢弃预览并移除卡片（沿用现状）。不设 `applying`：应用是同步提交，没有可观察的中间态。确认与取消在状态转换时同步防重，动作键为 previewId，不用轮次下标。`onApplyRevise` 保持 void 返回，调用完成即视为已提交到行程 store；本机存档失败沿用现有全局提示，不改上层状态接口。

## 7. 验收标准

- AC-01：给定一份包含地点、时间和费用增减、待确认事项的预览，A2UI 卡片与旧卡片呈现相同内容和单位，三端均可见。
- AC-02：确认一次只应用对应的原始预览一次；连续点击、重复 Action、同一轮内后一次预览覆盖前一次、以及多轮预览均不造成重复应用或串行程。
- AC-03：取消后行程未变化，该轮预览卡片移除且不再出现确认入口；已应用的卡片显示「已写进行程」且不能再次应用。
- AC-04a（真机可达）：同一页面内先后生成两份预览，确认第一份后再点第二份的确认，拒绝应用并提示重新生成。
- AC-04b（测试覆盖）：行程切换、在行程页改计划后回到对话的场景，真机不可达（预览不持久化且对话页会卸载），由测试构造行程身份或方案变化验证拒绝逻辑。
- AC-05：强制转换失败、未知组件或渲染异常时展示旧卡片；确认和取消仍遵循 AC-02 至 AC-04b。
- AC-06：服务端流式与非流式返回同一预览时，结果、展示及动作一致；模型失败使用引擎兜底时显示来源提示。
- AC-07：不改动现有服务端响应、规划计算和本机持久化语义；A2UI 处理失败不触发第二次模型请求。
- AC-08：Web、iOS、Android 各完成首页进入助手、生成或加载固定预览、确认和取消的实际运行验证，并保留截图或录屏；同时核对长文本及状态展示。须额外核对：确认后仍停在对话页、卡片显示「已写进行程」、「去行程页核对」可跳转且行程页内容与预览一致；以及 AC-04a 的双预览过期路径。
- AC-09：`lynx` 类型检查、构建及现有测试通过。纯函数层必测：消息适配器、动作白名单、防重、过期判定、previewId 路由。渲染层降级（转换失败、未知组件、渲染抛错）由 AC-08 的三端真机验收覆盖，本期不新建组件渲染测试基建。

## 8. 实施顺序与交付

1. 安装 `@lynx-js/genui@0.8.0` 及 peer `@lynx-js/lynx-ui`，锁定 `@lynx-js/react` 于 0.126.x（`@lynx-js/react-signals@0.0.7` 的 peer 上限为 0.129）；用固定消息加一个自定义 catalog 组件验证最小 A2UI surface 和动作，三端各跑一次，记录 bundle 体积增量。此步不碰业务逻辑。
2. 抽出现有预览卡及共享业务动作入口，确认重构前后行为一致；按 §9 调整确认后的导航（留在对话页 + 「去行程页核对」入口），并单独验证该改动不影响行程页数据。
3. 实现 Catalog、消息适配器、独立 store 和 fallback。
4. 加入 previewId、基准比较与 `pending / applied / stale` 状态转换；不做 applying 与卡片级失败反馈。
5. 完成自动化验证和三端实际运行验收；记录依赖版本、测试结果及已知限制。

交付包括代码、依赖锁文件、必要的测试、三端验收证据以及回退方式。第一期通过后，再另立规格评估让模型选择组件、服务端传输 A2UI 消息与更多卡片；不能将后续能力当成本期验收项。

## 9. 口径裁决（2026-11-17，已确认）

| 问题 | 裁决 | 影响 |
| --- | --- | --- |
| 确认后是否留在对话页 | 留在对话页，卡片显示「已写进行程」，另给「去行程页核对」入口 | 改 `lynx/src/App/subPages.tsx` 的 `onApplyRevise`，去掉 `p.back()` / `p.setTab('itinerary')`；FR-2、AC-03 的已应用态因此有落点 |
| 过期保护的验收方式 | 保护照写；同一页面内可达的部分走真机，跨页面部分用测试构造 | AC-04 拆为 a / b 两条 |
| 取消后卡片是否保留 | 消失，沿用现状 | 删除 `cancelled` 状态；AC-03 相应改写 |
| `applying` 中间状态 | 删除 | 应用是同步提交，无中间态；不做卡片级失败反馈 |
| 无障碍名称 | 本期删除该要求 | 全仓 0 处先例，AC 无对应项 |
| 测试分层 | 纯函数层必测，渲染层降级由三端真机验收覆盖 | AC-09 改写 |

连带口径（由上述裁决推导，实施时按此执行）：「已写进行程」表示已提交到当前行程 store，不等于已落盘。本机存档失败沿用现有全局提示（`useTrips` 的一次性 toast），卡片不单独表达失败，也不因此改 `onApplyRevise` 的返回类型。
