# Funny+ 产品方案：A 版小范围验证

> **状态**：产品草案，已确认首批范围；具体规则仍有待决事项。以下是目标，不代表当前代码已实现。
>
> **依据**：`PRODUCT.md`、`README.md` 和本次选定的方案 A。原始 PRD 未在当前会话中取得，标为建议的内容不能视为已确认需求。

## 一、产品定位与范围

**目标**：帮助没有时间做攻略的用户，把出游需求变成可比较、可修改、有依据的旅行计划。差异化不只是生成文案，而是让预算、路线与提示有计算依据和信息来源。

| 项目 | 方案 |
|---|---|
| 首批平台 | 移动端优先的 Web H5；小程序及 App 暂不属于本次交付范围 |
| 首批场景 | 重庆、成都的 **1–2 天**出游，优先验证周末出游，也覆盖有此需求的组团用户 |
| 后续目标 | 保留 3–5 天深度游目标，暂不在 A 版开放或作为 A 版验收范围 |
| 本次不做 | 账号、云档案、分享页、多人协作、预约提醒、交易跳转、足迹徽章 |

已按本方案实现：创建页只开放 1–2 天、人数按 1–8 实际值计算、偏好参与排程（无法映射时在方案里明说）、补充要求明确标注本期不参与排程。

## 二、核心流程

发现 → 填写需求 → 比较 2–3 套方案 → 选择行程 → 按天查看与修改 → 查看路线、预算和避坑信息 → 本机保存。

| 环节 | 产品目标（草案） |
|---|---|
| 填写需求 | 输入目的地、天数、实际人数、预算、偏好、交通方式和补充要求。以实际人数参与计算，不用人数区间冒充精确人数；不支持的目的地明确说明。 |
| 生成与比较 | 对同一组需求提供 2–3 套方案，说明节奏或交通方式的区别，并展示总价、人均、路线和主要风险。偏好及补充要求不能被静默忽略；数据不足以形成方案时的具体处理待定。 |
| 逐日行程与路线 | 按天展示地点、时间、停留和交通安排；空天不能作为完整安排。路线耗时需区分可追溯数据与估算，不将示意路线当作导航结果。 |
| 预算 | 按交通、住宿、门票、餐饮和其他费用展示总额、人均与计算依据，说明不包含的费用及不确定项；缺少依据时不伪造精确价格。 |
| 规则校验 | 对已校验、存在冲突、无法核验的内容加以区分；缺少依据时不能声称已通过。日时长、步行强度、超预算等阈值尚待产品确认。 |
| 局部修改 | 围绕指定的一天修改，并重新计算受影响的路线、预算和变更影响；未识别的指令不应静默改动行程。**建议**无明确天数时使用当前天、明确指定天数时以指令为准，此优先级待确认。 |
| 本机保存 | 多行程与变更记录保存在本机浏览器；成功写入后才算保存成功。首期的变更记录不等于已确认提供版本回滚。 |
| 避坑信息 | 按城市查看信息，并给出来源、核验时间、适用范围、有效期和可信状态；缺失的字段不伪造。已定 A2：过期内容默认不展示。 |
| 避坑反馈（A2 已实现） | 每条避坑可匿名提交「我也遇到了 / 不适用」，可附一句补充，同一浏览器只能提交一次；展示聚合计数。**仅计数，暂不自动影响可信状态**（加权规则待定）。 |

产品定位为大模型理解需求、程序计算和校验；当前实现仍是确定性模板。是否在 A 版验证时接入真实模型，以及具体模型、地图和价格来源，尚未确认；产品对外表述须与实际能力一致。

## 三、验收场景（草案）

| 场景 | 预期 |
|---|---|
| 覆盖范围 | 重庆、成都的 1 天或 2 天需求可进入 A 版流程；其他目的地明确说明未接入，3–5 天不作为 A 版开放范围。 |
| 人数与费用 | 输入 3 人或 8 人时，以对应实际人数计算；总额、分项及人均口径一致，不将 8 人按 6 人计算。 |
| 方案比较 | 数据充分时，可比较 2–3 套方案的主要差异、费用和风险；无法核验的内容不展示为已核验。 |
| 修改目标天 | 如确认上述优先级：查看第 2 天时发送不含天数的单日修改，应针对第 2 天；其他天的日程不被意外改动。 |
| 交通方式与变更 | 选择包车方案后，非交通方式的局部修改不能把交通预算改按公共交通计算；景点变化后须重新计算受影响的路线及预算。 |
| 本机保存 | 写入成功后，同一浏览器重新打开可查看已保存行程与变更记录；写入失败时不能视为保存成功。 |

## 四、数据与真实性

- 地点、营业信息、票价、住宿和路线耗时需要有适用范围、来源及核验或更新时间；未知、估算和已核验不能混为一谈。
- 模型可以提出候选，不得把模型编造的地点、价格、开放时间或路线当作事实。当前固定单价和直线耗时只适合作为原型数据。
- 若用户需求发送给外部模型或地图服务，需明确相关数据的处理范围与保留规则；供应商能力、费用、授权和隐私要求尚未核验。

## 五、待确认的产品口径

| 决策 | 待选项或问题 |
|---|---|
| 过期信息 | **已定 A2**：默认不展示，并告知有 N 条未展示。 |
| 待核实信息 | 默认展示并区分状态，还是默认不展示？这是独立于是否过期的判断。尚未确认。 |
| 行程存在冲突 | **已定 B1**：允许保存并保留冲突状态。 |
| 候选方案不足 | 数据不足、方案数量不足 2 套，或预算等条件无法满足时，如何向用户呈现和处理？ |
| 规则阈值 | 日时长、步行强度、预算偏差、车辆核载和异常情况的判断规则与阈值是什么？现有代码常量不自动视为已确认口径。 |
| 模型与数据 | A 版是否接入真实模型、地图和价格数据？哪些数据必须在对外验证前完成核验？ |
| 反馈加权 | 反馈计数是否影响「可信状态」？若影响，多少条 `遇到` 才升级、多少条 `不适用` 要降级？现有实现只计数不改状态。 |

**建议增加（原 PRD 未核实）**：出行日期、成人/儿童人数，有助于判断营业时段及票价；是否纳入 A 版、是否必填，等待确认。

**建议的验证问题（不预设指标阈值）**：用户能否理解方案区别、是否信任费用依据、修改后能否看懂影响；数据采集方式另行确认。
