# PRD V0.2：交通决策与 POI 级信息

| 项 | 内容 |
|---|---|
| 版本 | V0.2（取代 `docs/requirements-transport-poi.md` 中间稿） |
| 状态 | 待评审 |
| 范围 | 在 V0.1（重庆/成都 1–2 天）之上新增两条能力：**景区交通的约束与选择**、**POI 级现场信息** |

| 不在本文件 | 交易、账号、分享、多人协作（沿用 V0.1 的排除项） |

## 一、问题定义

用户不是缺攻略，是**缺执行期的判断依据**。

| 场景 | 事实链 | 断点 |
|---|---|---|
| A 大理海东 | 小红书给到「大致路线 + 要买观光车票」→ 现场坐车 → 才发现有班次、乘车点限制；同行人多，票钱超过打车 | ① 约束不可见 ② 缺「该不该换方式」的判断 |
| B 到景点后 | 人已在龙龛码头 → 打开产品 → 只给「大理」级攻略 | ③ 信息粒度对不上人所在的位置 |

断点①②导致**行程作废或白花钱**（高损失、低频、强情绪）；断点③导致**产品在用户最需要的那一刻没用**（高频、低损失、低留存）。

**本版要解决的是①③，②只做「够了就说结论」的程度。**

## 二、目标

### 业务目标
让「生成出来的行程」具备**可执行性**——用户拿着它出门，不会被班次、乘车点、票种打回。

### 用户目标
- 出发前：知道这张票什么时间不能用、几个人该换车。
- 到现场：打开就知道这个点怎么进出、有什么坑、能吃在哪。

### 成功标准（不做主观形容词）
| 指标 | 定义 | 目标 |
|---|---|---|
| 冲突拦截率 | 保存前被提示并修改的行程冲突 / 全部检测到的冲突 | ≥ 60% |
| 建议采纳率 | 点「切换为建议方式」/ 看到建议 | ≥ 25% |
| POI 详情打开率 | 从行程条目进入 POI 详情 / 有 POI 的行程条目曝光 | ≥ 40% |
| 空态补全率 | 出现「暂无数据」后 7 日内该条目有数据的比例 | 首版不设目标，仅观测 |
| **误报率**（反指标） | 用户点「这条不对」的提示 / 全部硬提示 | ≤ 10% |

不追的指标：内容产出量、日均停留时长、注册转化。

## 三、用户与场景

| 角色 | 特征 | 进入方式 | 核心任务 |
|---|---|---|---|
| 组队出行者（4–8 人） | 已在小红书看过攻略，决策慢、对钱敏感 | 创建行程后 | 判断该不该买景区交通票 |
| 现场用户 | 已到达具体点位，边走边查 | 行程条目 → POI 详情 | 解决「现在怎么走 / 吃哪 / 别踩什么」 |

两条场景共享同一批底层数据：一个地点既有营业时间，也有班次、票种、坑和吃住。

## 四、范围与优先级

| 优先级 | 内容 | 理由 |
|---|---|---|
| **P0** | FR-01 线路与班次 / FR-02 硬约束校验 / FR-03 人数差量结论（区间版） / FR-04 POI 详情（只做「进出 + 坑」两组） / FR-05 提交与即时回填 / FR-06 状态语言 | 缺任一环，闭环不成立：没有 01/02 用户继续踩坑，没有 05 空态永远填不平，没有 06 会对外撒谎 |
| **P1** | FR-04 的「吃 / 住」两组、更多线路、替代方案精细化、模型接入 | 依赖数据积累 |
| **P2** | 实时班次、UGC 内容流、评价体系 | 无数据源 / 偏离定位 |

**首版只做深一条线路（大理海东），不做宽。** 铺 20 个城市 = 20 个「暂无数据」；把一条线打到 100% 覆盖才能证明这套模型成立。

## 五、功能需求

### FR-01 线路与班次

**用户故事**：作为组队用户，排行程时我要看到观光车的站点、末班和票种，才不会把日落排到 19:00 还指望坐车回来。

**交互**
1. 行程中涉及的交通段如果是线路型（观光车 / 摆渡车 / 索道 / 城际班车），展示线路摘要：站点顺序 · 首末班 · 间隔 · 票种价 · 是否需提前购票。
2. 线路卡可展开看全部站点，点站点跳到该 POI 详情（接通 FR-04）。

**数据要求（最少字段）**
`线路名 / 城市 / 有序站点 / 首班 / 末班 / 发车间隔 / 票种与票价 / 是否需提前购票 / 单班核载 / 来源 / 核验时间`

**规则**
- 线路是独立实体，不是给地点加字段——观光车存在的原因就是这些点连成一条线。
- 一条线路至少 2 个站点才算成立，单站点线路视为数据错误。

**验收**
选「大理海东 + 观光车」，线路卡出现末班时间；把行程排到末班之后 → 见 FR-02。

---

### FR-02 硬约束校验与替代建议

**用户故事**：我不想在保存前被放行一个到站已无车的行程。

**判定顺序（严格按序，不可跳）**
1. **硬约束**：末班 / 首班 / 需提前购票 / 预约时段 → 违反即 `error`，先解冲突再说别的。
2. **等待成本**：到站时间与最近班次的间隔，超过入选间隔的 2 倍 → `warn`。
3. **软约束**：日时长、步行强度、超预算 → 沿用 V0.1 现有规则。

**替代建议**
出现 `error` 时必须同时给至少一条替代：提前到某时刻 / 换交通方式（接 FR-03）/ 换景点。无法给出替代时，明确写「暂无可替代方案，请手动调整」。

**每个硬提示必须带「这条不对」按钮**——否则误报率无法测量，也无法自证清白。

**未核验数据不产生 error**：来源为「用户填报」或「暂无数据」时，最多 `warn` + 标「待确认」。

**验收**
| 场景 | 预期 |
|---|---|
| 末班 17:00，行程 18:30 到站，来源=官方 | error + 替代建议 |
| 同上，来源=用户填报 | warn + 「待确认」，行程可保存 |
| 末班数据缺失 | 不报错，显示「暂无末班时间 · 你可能排到 19:00 却无车可回」+ 补充入口 |

### FR-03 人数 → 交通结论

**用户故事**：作为 5 人团队，我要一句话告诉我这段打车还是坐观光车，差多少钱、差多少时间。

**交互**
- 位置：方案对比页每套方案下、行程内线路型交通段下。
- 形式：一行结论 + 可展开的依据。

**硬规则**
1. **不做 1–3 / 3–5 固定档**。同人数换动线结论会反过来，写死即错。
2. **钱与时间并列展示，不合成综合分**。
   > 「5 人：打车 2 辆 ≈ ¥120，等车约 5 分钟｜观光车 5 张 ¥125，等车约 20 分钟」
   
   合成「等于多少钱」需要引入主观时间单价，会把不确定包装成精确。宁可两项并排，让用户自己定权重。
3. **数据不全降级为区间**，并标清假设：「按 4 人/车、¥60/车估」。不许输出伪精确值。
4. 缺票价或缺核载 → 只做单维度对比，并标明「仅比了票价，未计时间」。

**验收**
| 场景 | 预期 |
|---|---|
| 4 人，环海长动线 | 结论偏打车 |
| 4 人，短动线 + 高班次密度 | 结论偏观光车 |
| 两者结论不同且理由可读 | 通过 |

### FR-04 POI 详情：吃 / 住 / 进出 / 坑

**用户故事**：作为已经在龙龛码头的用户，我只想看跟龙龛码头有关的信息。

**入口**：行程条目点击 / 线路卡站点点击。**不做**「按城市翻列表」作为主入口（保留为兜底）。

**结构**：固定四组，顺序 **坑 → 进出 → 吃 → 住**（P0 只做前两组）。顺序理由：现场用户最先要的是「别踩坑」和「怎么走」，吃住是驻留后才产生的需求。

**规则**
- 每条必须挂到具体 POI。
- 区域级信息（如「海东片区」）可下沉到该区 POI 展示，但**必须显式标注适用范围**，否则用户会以为只对本点有效。
- 每组独立空态：`暂无 · 到过这里？补一条`（接 FR-05）。
- 复用现有 facts 的 `source / verifiedAt / trust / validUntil`，不新造可信度体系；过期条目不展示并告知「有 N 条过期信息未展示」。

**验收**
点开龙龛码头：只出现覆盖它的条目；区域级条目带「适用于整个海东片区」；不出现大理古城条目。

### FR-05 数据提交与即时回填

**用户故事**：我刚在才村码头看到末班车牌子，愿意花 20 秒告诉产品。

**这是空态的唯一出路，属于 P0 主干，不是附加功能。**

**交互**
| 项 | 要求 |
|---|---|
| 字段 | ≤3 个输入（补什么 / 补的值 / 可选来源），无注册、无弹窗套弹窗 |
| 预填 | 从触发位置带入上下文（哪个 POI、哪个字段缺） |
| 提交后 · 自己 | 立即在其视图生效，标「你提交的 · 待核验」 |
| 提交后 · 他人 | 进入池，他人可见，标「用户填报」 |
| 参与计算 | 可 `warn`，不可 `error` |
| 反滥用 | 同 clientId 同条目去重（现有 `/api/facts/feedback` 已具备），不加验证码 |

**激励设计**：动力来自「填完立刻改善我自己的行程」，不是「帮助他人」。因此**先回填自己的视图，再入库**，顺序不可反。

**验收**
提交末班时间后，返回行程：冲突提示从「暂无数据」变为「待确认」，并显示提交来源；换个 clientId 打开同行程可见该条标「用户填报」。

### FR-06 状态语言（横切）

任何数字或结论旁必须有状态，**不允许裸数字**。

| 状态 | 展示 | 参与计算 |
|---|---|---|
| 已核验（有来源 + 未过期） | 正常 + 来源 + 核验时间 | 可判 error |
| 用户填报 | 显式标「未经核验」 | 最多 warn |
| 暂无数据 | 「暂无 · 影响：xxx」+ 补充入口 | 不参与，行程标待确认 |

**空态文案必须带影响**。「暂无末班时间」= 用户离开；「暂无末班时间 · 你可能排到 19:00 却无车可回」= 用户知道该补什么。

## 六、模型能力要求

**结论：P0 不接模型，P1 再接。** P0 的价值在「约束可见 + 能补齐」，表单和规则就能兜住；为了接模型而接，会把确定性优势换成不确定性。

| P1 用在哪 | 边界 |
|---|---|
| 把「补充要求」解析成结构化需求（人数 / 想坐观光车 / 带老人） | 不产出价格、班次、坐标、营业时间 |
| 数据缺口时生成追问（该问什么、怎么问） | 不判定冲突 |
| 把算好的结果组织成解释语句 | 不改变数值 |

模型输出必须落进既定结构；落不进去退回表单，不硬猜。模型失败或超时 → 走 P0 路径，不阻塞主链路。

## 七、数据要求（mock 规范）

| 规则 | 说明 |
|---|---|
| mock 必须带状态 | 开发环境 mock 标 `pending`，不得标 `official` 冒充官方 |
| 保留 1 份演示数据 | 一条线路标 `official`，专供演示 error 态与冲突拦截 |
| 缺失即缺失 | 缺字段就留空走「暂无数据」，不用估算值填坑 |
| 一致性 | 线路站点必须是真实 POI id，不新增平行地点 |

## 九、里程碑

| 阶段 | 交付 | 判定 |
|---|---|---|
| M1 | mock 一条线路 + FR-01/02/06 | 冲突能拦截、误报可控 |
| M2 | FR-04（坑/进出）+ FR-05 | 空态可被填平且本人立刻受益 |
| M3 | FR-03 区间版 | 同人数不同动线结论可翻转 |
| M4 | FR-04（吃/住）+ 第二条线路 | 模型复制到新线路，不靠人肉特判 |
| M5 | 模型接入（P1） | 解析失败可无损降级 |

## 十、风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 数据缺失率高，页面全是「暂无数据」 | 产品被判定没用 | 只承诺有数据的线路；单线路做到 100% 覆盖 |
| 硬提示误报 | 用户关掉提示，产品失去护栏价值 | 只有 `official` 能判 error；每个提示带「这条不对」 |
| 用户提交的是错的 | 错误扩散 | 未核验不产生 error；标注来源，不做审核队列 |
| 人数结论被当成承诺 | 出错后背锅 | 永远并列展示假设与区间，不给单一结论值 |

## 十一、待确认

| 项 | 建议 |
|---|---|
| 用户提交数据默认是否对他人可见 | 可见但降权（experience 级），不做审核队列 |
| POI 详情是半屏还是独立页 | 半屏，保留行程上下文 |
| 是否对外承诺大理 | 先做 mock 样板验证，不写进对外能力清单 |
| 时间成本是否给一个默认折算价 | **不建议**。并列展示，让用户自己权衡 |
