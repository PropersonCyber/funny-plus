# 11-17-gulu-ground-facts

## 背景
- 咕噜已经能生成方案，并和行程页共用同一套修改预览。它还解释不了营业、票价、避坑和费用依据，硬冲突也不会自己收一版，离开页面对话就丢。

## 目标
- 问事实时，答案来自引擎工具，未核实票价不被说成免费。
- 生成方案若有硬冲突，最多再松一版；第二次仍冲突就停止，不覆盖已保存行程。
- 同一行程再次打开咕噜，能看到上次的对话文字。

## 变更
- 对话增加只读工具：`getPlaceDetail`、`getFacts`、`getBudget`、`listLines`、`validatePlan`。
- `generatePlans` 的结果带上 `checks`，用 `attempt` 限制重试。
- 对话文字按行程写入本机 `funny-plus.chat.v1`。选定新方案时，这段对话跟到新行程。

## 影响范围
- 页面/模块: 咕噜对话页、行程创建出口
- 数据/API: `POST /api/ai/chat` 的工具返回增加事实字段和 `checks`；不新增 HTTP 路径，不改错误码
- 权限/安全/资金: 无
- 兼容性: 旧客户端忽略新增字段。对话记录是新 key，不影响已有行程存档

## 不做范围
- 到达判断、下一站、账号与跨设备、旅行回忆、攻略分享
- 表单生成改为模型提案
- 把方案卡片本身存进对话记录

## 已确认决策
| 决策点 | 结论 | 来源 |
|--------|------|------|
| 范围 | 解释工具、冲突回喂、本机会话 | 用户确认 |
| 排除 | 到达、下一站、账号、回忆、分享、表单主链路 | 用户确认 |

## 验收
- `npm test` 覆盖：未核实票价保持 null、过期避坑只计数、第二次冲突的停止文案、草稿对话跟到新行程且旧行程记录还在
- `npm run typecheck`（lynx 与 server）通过
- 真实模型对话未在本次自动跑通，需本机 API 带 `AI_API_KEY` 后人工问一句票价和「一天排太满」

## 风险与回滚
- 模型仍可能不调用工具就写数字。提示词约束不是证明。回滚时去掉新工具和本机 key 即可，行程存档不受影响。
